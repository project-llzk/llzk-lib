55def TemplateMonomorphizationPass : LLZKPass<"llzk-monomorphize-templates"> {
56 let summary =
57 "Specialize structs and free functions reachable from llzk.main";
58 let description = [{
59 Starting with a concrete `llzk.main`, discover and instantiate struct and
60 free-function dependencies until every requested specialization has been
61 processed. Reuse definitions by source symbol and concrete argument list,
62 including reachable definitions with no template parameters. Free-function
63 arguments may be explicit on a call or inferred from its type signature.
64 Preserve source templates and control flow, and update direct type uses and
65 calls to their concrete definitions. A free-function call retained in an
66 unselected branch receives a concrete callee only when struct type rewriting
67 changes its signature.
68
69 Loops remain in the IR rather than being unrolled; discovery evaluates their
70 iterations to identify specializations without expanding the loop bodies.
71 "Rolled" calls and struct types below retain affine parameters that depend on
72 those iterations or on array element indices.
73
74 Affine calls and array values retain their parameterized types. Their
75 `poly.family_specializations` and `poly.family` attributes identify the
76 concrete definitions needed by later elaboration; definitions carry
77 `poly.specialization_id`, `poly.origin` and `poly.arguments` attributes.
78 Free-function clones carry `poly.origin` and `poly.arguments`; their
79 identities are separate from the struct IDs used by families.
80 `poly.family` appears on members and operations producing an array value,
81 including `struct.readm` and `array.new`. Each entry names the rolled struct
82 type, the enclosing array's index tuple, and the matching specialization.
83 The `type` entry retains the original affine-parameterized family type; it
84 identifies which struct field is being specialized within a POD element.
85 `specialization` identifies the concrete clone through its
86 `poly.specialization_id`. For example, an element at index 2 of a Child<i>
87 family retains Child<i> in `type` and names the clone whose `poly.arguments`
88 are [2]. Concrete sibling fields have no family entry.
89 On a rolled call, `poly.family_specializations` lists candidates collected
90 from all matching arrays and affine calls in the source instance. The list
91 may be empty only when a known array has an empty dimension. A consumer
92 selects a target by evaluating the argument type's affine map using the
93 value's affine inputs, often an array element's indices, and matching the
94 resulting arguments to `poly.arguments`.
95 `poly.origin` and every struct name nested in `poly.arguments` are relative
96 to the outermost `llzk.lang` root, which is also the lookup anchor when
97 reloading this metadata. Cache keys use the same argument spelling, so
98 requests from different roots reuse the same specialization. Substitution
99 re-spells type arguments relative to the clone's root; an argument whose
100 definition is outside that root is diagnosed at the instantiation site.
101 Arguments to typed `poly.param` declarations are converted to the declared
102 type using the conversions below, before forming a cache key. An
103 incompatible argument is diagnosed. Felt-to-index conversion requires a
104 value in the nonnegative signed 64-bit index range. Arguments to felt
105 parameters with a known field are reduced modulo its prime before forming
106 the cache key and substituting uses. A felt literal with no specified field
107 acquires the parameter's declared field; a different explicit field is
108 rejected. Equivalent field values therefore share a specialization. With no
109 known field, index-to-felt conversion requires a nonnegative value and
110 preserves it. Untyped parameters retain their input
111 attributes, so differently spelled numeric values can create distinct
112 specializations. An `i1` parameter accepts only boolean arguments or index
113 zero and one, which become false and true. Other index values fail type
114 conversion at the instantiation site. The normalized boolean binding
115 determines specialization identity and is used for every read and forwarded
116 argument.
117 Forwarding that value to an index parameter produces zero or one.
118 A felt binding must be read with its exact felt type, including its field,
119 even for untyped parameters. Mismatched felt types are diagnosed at
120 `poly.read_const`.
121 Reading it as index or i1 is diagnosed at `poly.read_const`; use an explicit
122 cast after a felt read for numeric conversion. Integer bindings read as i1
123 must be zero or one. Integer-to-felt reads use the same modular conversion
124 as typed arguments, and negative values require a known field modulus.
125 Reads whose type is a type variable use its concrete binding.
126
127 Discovered methods and free functions must be defined and single-block.
128 Supported regions are `scf.if`, signed `scf.for` with known bounds and
129 positive steps, and `scf.while` with a known condition at every check.
130 Unstructured branches are diagnosed. Constant evaluation uses template
131 bindings and fold hooks; global and aggregate reads and call results remain
132 unknown. Function arguments also begin unknown, even when a caller passes
133 a constant. Required specialization arguments must resolve.
134 External free functions retain their declared signatures. Calls with struct
135 types rewritten to distinct clone types are diagnosed, including plain
136 structs, because the declaration would otherwise have a mismatched type.
137 Includes must be inlined before running this pass.
138 }];
139 let options =
140 [Option<
141 "specializationLimit", "max-specializations", "unsigned", "1000",
142 "Maximum number of concrete struct and free-function definitions">,
143 Option<"evaluationLimit", "max-evaluation-steps", "uint64_t", "1000000",
144 "Maximum steps shared by template expressions and methods in one "
145 "discovery run">];
146}

149 let summary = "Flatten structs and unroll loops";
150 let description = [{
151 Performs the following transformations:
152 - Instantiate `affine_map` parameters of StructType and ArrayType
153 to constant values using the arguments at the instantiation site
154 - Replace parameterized structs with flattened (i.e., no parameter)
155 versions of those structs based on requested return type at calls
156 to `compute()` functions and unroll loops
157 - Unroll loops
158 }];
159 // Implementation note: These options should be kept in sync with

162 [Option<"iterationLimit", "max-iter", "unsigned",
163 /* default */ "1000",
164 "Maximum number of times the pass will run if a fixpoint "
165 "is not reached earlier. Unrolling loops can provide more "
166 "opportunities for instantiating structs but the converse "
167 "is true as well. Thus, the pass will run multiple times "
168 "until no further changes can be made or the upper limit "
169 "provided in this option is reached.">,
170 Option<"cleanupMode", "cleanup",
171 "::llzk::polymorphic::FlatteningCleanupMode",
172 /* default */
173 "::llzk::polymorphic::FlatteningCleanupMode::Unspecified",

179 stringifyFlatteningCleanupMode(::llzk::polymorphic::FlatteningCleanupMode::Disabled),

194def WildcardArraySpecializationPass
195 : LLZKPass<"llzk-specialize-wildcard-arrays"> {
196 let summary =
197 "Refine wildcard array casts and specialize concrete call targets";
198 let description = [{
199 Refines `poly.unifiable_cast` results when wildcard `array.type` dimensions can be replaced
200 with concrete integer sizes from the input type. Then specializes free functions, extern
201 declarations, and whole structs for calls whose wildcard array dimensions have become concrete.
202
203 This pass is intended to run after `llzk-flatten`. It iterates to a fixpoint so newly-refined
204 cast result types can enable further callable specialization in later iterations.
205 }];

208 "Maximum number of iterations before the pass gives up "
209 "reaching a fixpoint.">];

212def TypeVarInferencePass : LLZKPass<"llzk-infer-tvar"> {
213 let summary = "Infer concrete function types for polymorphic type variables";
214 let description = [{
215 Infers concrete replacements for `!poly.tvar` template parameters from operations in
216 `function.def` or `poly.expr` bodies, such as `poly.unifiable_cast` between a type variable
217 and a more concrete type (which means for maximum effect you should run it before other
218 optimization passes that can remove `poly.unifiable_cast`). Rewrites affected function
219 signatures and body types, removes redundant casts, drops resolved `poly.param` declarations,
220 and updates call-site template parameter lists.
221
222 The pass also creates template-local instantiated versions of functions for each
223 type-variable replacement. The `llzk-flatten` pass performs similar instantiation of type
224 variables but only as part of its more extensive lowering and flattening, all of which may
225 not be desired in some cases (hence the utility of this pass).
226
227 This pass may result in `poly.template` containing no `poly.param` or `poly.expr`. Run
228 `llzk-drop-empty-templates` after this pass to simplify these templates.
229 }];
230}
